One rent question. Six moving parts.

This app answers a very human question: “Is this apartment rent wildly off?” Under the hood, it turns a simple form into a guided trip through a component, two tiny API routes, a calculation engine, and 104,700 benchmark rows.

Module 2 · Meet the cast 02

The frontend is the conductor, not the calculator.

The biggest file in this repo is RentCheckClient. That is not because it contains all the business truth. It is because it choreographs the user experience: language, autocomplete, validation, form submission, and result display.

RentCheckClient

Browser orchestrator

This is the air traffic controller. It does not own the rent math, but it decides when searches happen, when errors appear, and when the result card scrolls into view.

  • Keeps UI state like query text, selected city, surface area, monthly rent, and loading flags.
  • Makes two network requests: one for suggestions and one for the final verdict.
  • Protects the user from bad input before the server is even contacted.
Code · rent-check-client.tsx 
  useEffect(() => {
    if (selectedLocation && query === selectedLocation.displayName) {
      setSuggestions([]);
      return;
    }

    if (query.trim().length < 2) {
      setSuggestions([]);
      return;
    }
Plain English

If the user already chose a suggestion and has not changed it, stop searching again.

If the user has typed fewer than two characters, also stop.

This is a tiny example of protecting the server from pointless work.

Why this file matters for AI steering

If you ask an AI tool to “add a new field,” this is the file that probably grows first. Knowing that helps you give better instructions, like “add a furnished/unfurnished toggle to the client form, then include it in the POST payload.”

Aha!

A large UI file is not automatically a bad smell. The real question is whether it owns too many kinds of responsibility. Here, the app keeps math in the domain layer, which is a healthy split.

Module 3 · How pieces talk 03

Two route handlers keep the network story tiny.

The outside-world metaphor here is a ticket counter. The browser fills out a slip, the counter checks it, then either rejects bad input fast or forwards the request to the real logic.

Message flow in one glance

1 · Browser User types

The client sends a GET request to `/api/locations` after a short pause.

2 · Search route Find matches

The route delegates to the repository and returns JSON suggestions.

3 · Browser User submits

The client sends a POST request with location key, size bucket, surface area, and monthly rent.

4 · Rent-check route Validate first

Bad selections or impossible numbers are rejected before any heavy work happens.

5 · Domain layer Compute result

If the data exists, the route builds a verdict and responds with a ready-to-render result object.

Code · app/api/rent-check/route.ts 
  if (!locationKey || !segment || !isFormSegment(segment)) {
    return Response.json({ errorCode: "invalid_selection" }, { status: 400 });
  }

  if (!Number.isFinite(surfaceArea) || surfaceArea <= 0) {
    return Response.json({ errorCode: "invalid_surface_area" }, { status: 400 });
  }
Plain English

If the selected city or home-type bucket is missing or fake, stop immediately.

If the surface area is not a real positive number, stop immediately again.

This keeps nonsense from reaching the real calculator and makes error messages specific.

Why thin APIs are powerful

A thin API layer is easier to reason about. It mostly says: “Is this input believable? If yes, ask the right helper. If no, explain why.” That gives you a clean place to add permissions, rate limits, or analytics later.

Best debugging instinct here

Separate validation bugs from calculation bugs. A 400 response means the request shape is wrong. A strange but valid verdict means the domain rules or the benchmark record deserve inspection.

  async getBenchmark(locationKey: string, segment: FormSegment): Promise<RentBenchmarkRecord | null> {

Plain English

Ask for the in-memory index of benchmark rows.

If nothing matches, return `null` so the route can answer with a clean error.

Why this design is smart for an MVP

Shipping with local files avoids the cost and complexity of a live database. The repository pattern means the app can later swap CSVs for PostgreSQL without rewriting the whole UI.

Module 5 · The clever trick 05

The calculator quietly adjusts for apartment size.

The metaphor here is tailoring a suit. The benchmark is the standard size on the rack, but the app nudges the price up or down depending on whether the real apartment is much smaller or larger than the reference size.

Play with the size-adjustment rule

This mini lab uses the actual thresholds from the code. Smaller-than-reference apartments get a higher multiplier; bigger ones get a discount multiplier.

Reference size: 37 m² Current input: 37 m²
Multiplier: 1.00x Within the reference band, so no size adjustment. Adjusted benchmark: 18.00 €/m²
Code · src/lib/domain/rent-check.ts 
export function getSizeAdjustmentMultiplier(surfaceArea: number, referenceSurfaceM2: number): number {
  if (surfaceArea < 0.7 * referenceSurfaceM2) {
    return 1.08;
  }

  if (surfaceArea < 0.9 * referenceSurfaceM2) {
    return 1.04;
  }
Plain English

Start by comparing the apartment's size to the benchmark's reference size.

If the apartment is much smaller, raise the price-per-square-meter benchmark.

Why? Tiny apartments often cost more per square meter than roomy ones.

The full verdict formula

The app first computes an adjusted benchmark rent per square meter, then multiplies by the apartment's size, then compares the user's rent to that expected monthly rent. The verdict buckets are based on the percentage gap: below -10%, between -10% and +10%, between +10% and +20%, and above +20%.

Aha!

This is business logic, not presentation logic. If you ever need tests, this is one of the first files worth protecting with them because it encodes product meaning.

Module 6 · When things break + what's next 06

Raw government files become product data through a cleaning pipeline.

Think of this as a customs checkpoint. Messy semicolon-delimited source files arrive from the outside world, the Python script normalizes them, and only then does the web app trust them at runtime.

The data pipeline in one sweep

raw

`data/raw/`

Three French CSV files arrive with semicolons, accents, comma decimals, and inconsistent text.

clean

Python cleaner

Normalizes encodings, parses numbers, builds confidence levels, and deduplicates records.

runtime

Processed CSVs

Writes `locations.csv` and `rent_benchmarks.csv`, which the app reads directly at runtime.

later

Optional PostgreSQL

The importer and SQL schema are ready for a future database-backed version.

Code · clean_rent_benchmarks.py 
    high_mask = (
        (frame["prediction_level"] == "commune")
        & (frame["r2_adj"] >= 0.7)
        & (frame["nb_observations_commune"] >= 100)
        & (interval_width_ratio <= 0.30)
    ).fillna(False)
Plain English

Mark a benchmark as “high confidence” only if several quality checks all pass.

It needs the right prediction level, strong model fit, enough observations, and a narrow interval.

This is product judgment hidden inside data preparation, not in the UI.

Debugging map

  • Search broken? Look at the client debounce, then the repository's normalization logic.
  • Counts missing? Look at summary loading, processed files, and the CSV loader paths.
  • Verdict feels weird? Look at `getSizeAdjustmentMultiplier()` and `getCategoryLabel()`.
  • Deployment works locally but not on Vercel? Confirm processed CSV files were committed.

Big-picture architecture lesson

This project is a great example of a “good-enough now, upgradeable later” architecture. It avoids the weight of a database at the start, but the repository boundary, importer, and SQL schema leave a clear runway for the next stage.
